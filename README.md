# メールチケット管理

Gmail の問い合わせメールを Zendesk のようにチケットとして整理するアプリです。

**このアプリが解決すること**

共有のサポートアドレス（`support@…` など）を複数人で使っていると、Gmail の画面では
返信の差出人が全員同じアドレスになるため、**「この返信、誰が送ったんだろう？」** が
分からなくなります。休みの日に他の人が対応した分は特にそうです。

このアプリは 1 通ずつ送信者を特定して記録し、判別できないものは
「送信者不明」とはっきり表示します。その場で「これは○○さん」と指定すれば、
**次回から同じパターンを自動で見分ける**ようになります。

---

## 主な機能

| 機能 | 内容 |
| --- | --- |
| チケット化 | Gmail のスレッド 1 本 = チケット 1 件。件名の `Re:` 連鎖に振り回されません |
| 顧客ごとの履歴 | 同じ相手との**別件も含めた全やり取りを 1 本の時系列**で確認。自分が送った件と、他の人が別件で返した件が混ざって時間順に並びます |
| 送信者の特定 | 返信ごとに「誰が送ったか」を表示。判別方法（委任送信 / 署名 / アプリ送信）も分かります |
| 判別の学習 | 手動で直すとルールが自動追加され、過去のメールにも遡って適用されます |
| ステータス管理 | 対応中 / 保留 / 解決済み / クローズ、優先度、担当者の割り当て |
| 未返信の緊急度 | 顧客の最後のメールからの経過時間で **要対応 → 遅延 → 重大な遅れ** と自動で段階が上がります。手動の優先度とは別に表示するので、「自分で上げた」のか「放置して赤くなった」のかが区別できます |
| 絞り込み | 未返信・複数人が対応・送信者不明あり、担当者別、全文検索 |
| 返信送信 | アプリから返信すると送信者が確実に記録されます（Gmail のスレッドにも正しくぶら下がります） |
| 社内メモ | 顧客に見えないメモを時系列に残せます。返信ボタンとは別のボタンなので、誤って顧客に送ることがありません |
| 署名 | 担当者ごとに登録でき、返信の末尾に自動で付きます。署名に氏名が入っていれば、判別ルールとしても自動登録されます |
| 操作履歴 | ステータス変更・担当者変更・送信者の設定などをすべて記録 |

データはすべて手元の SQLite ファイル（`prisma/dev.db`）にのみ保存され、外部には送信されません。

## まず触ってみる（Google の設定は不要・2分）

いきなり Gmail に繋ぐ前に、サンプルデータで操作感を確認できます。

```bash
npm install
npm run demo     # .env とデータベースを自動で用意します
npm run dev
```

<http://localhost:3000> を開いて **「サンプルデータで試す」** を押すだけです。

サンプルには、まさに困っている状況がそのまま入っています。
「請求書の再発行をお願いします」を開くと、1本の会話に 3 種類の返信が混ざっています。

| 返信 | 画面の表示 |
| --- | --- |
| 自分がこのアプリから送った | ✓ このアプリから送信 |
| 齊藤さんが Gmail の委任送信で返信 | 委任送信から判別 |
| 誰かが Gmail から直接返信 | **送信者不明**（黄色い破線のバッジ） |

「送信者不明」のバッジを押して担当者を選び、署名の候補（`木村`）も一緒に選んで保存すると、
ルールが学習されて過去のメールにも反映されます。返信フォームも試せます
（デモモードでは実際のメール送信は行われず、記録だけが残ります）。

デモをやめるときは `.env` の `DEMO_MODE=1` を `DEMO_MODE=0` に戻してください。

## セットアップ手順（本番）

### 0. 必要なもの

- Node.js 20 以上（推奨: 22）
- Google アカウント（サポート用の Gmail）

### 1. 依存パッケージのインストール

```bash
npm install
```

### 2. Google Cloud で OAuth クライアントを作る

Gmail を読み書きするための鍵を発行します。5 分ほどで終わります。

1. [Google Cloud Console](https://console.cloud.google.com/) を開く
2. 画面上部のプロジェクト選択 →「新しいプロジェクト」を作成（名前は何でも構いません）
3. 左メニュー **「API とサービス」→「有効な API とサービス」** →
   上部の「+ API とサービスを有効にする」→ **Gmail API** を検索して有効化
4. 左メニュー **「API とサービス」→「OAuth 同意画面」**
   - User Type: **外部** を選択して「作成」
   - アプリ名・ユーザーサポートメール・デベロッパーの連絡先メールを入力して保存
   - **「対象」（テストユーザー）** の画面で、自分の Gmail アドレスを追加
     （※ここを忘れるとログイン時に「アクセスをブロックしました」と出ます）
5. 左メニュー **「API とサービス」→「認証情報」**
   - 「+ 認証情報を作成」→ **「OAuth クライアント ID」**
   - アプリケーションの種類: **ウェブ アプリケーション**
   - **承認済みのリダイレクト URI** に次を追加:

     ```
     http://localhost:3000/api/auth/callback
     ```

   - 「作成」を押すと **クライアント ID** と **クライアント シークレット** が表示されます

> **公開ステータスについて**
> このアプリは Gmail の「制限付きスコープ」を使うため、一般公開するには Google の審査が必要です。
> ただし **自分ひとり（テストユーザー）で使う分には審査は不要**です。
> 同意画面は「テスト」のままにしておいてください。
> テストモードではリフレッシュトークンが 7 日で失効するため、
> 週に一度ログインし直す必要があります（再ログインするだけで元に戻ります）。

### 3. 環境変数を設定する

```bash
cp .env.example .env
```

`.env` を開いて、次の 3 つを埋めてください。

```bash
GOOGLE_CLIENT_ID=手順2で取得したクライアントID
GOOGLE_CLIENT_SECRET=手順2で取得したクライアントシークレット
SESSION_SECRET=下のコマンドで生成した値
```

`SESSION_SECRET` は次のコマンドで作れます。

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

読み込む期間の初期値は「過去 180 日・最大 2000 通」です。変えたい場合は同じく `.env` の
`SYNC_DAYS_BACK` と `SYNC_MAX_MESSAGES` を編集してください（`SYNC_DAYS_BACK=0` で全期間）。

### 4. データベースを作る

```bash
npm run setup
```

### 5. 起動する

```bash
npm run dev
```

ブラウザで <http://localhost:3000> を開き、**「Google でログイン」**を押します。
権限の確認画面で「Gmail のメールの閲覧・作成・送信」を許可してください。

ログイン後、左下の **「Gmail と同期」** を押すとメールの読み込みが始まります。
初回は通数によって数分かかります。進捗はボタンの下に表示されます。

## 未返信の緊急度

顧客からの最後のメールに返信できていない時間で、自動的に段階が上がります。

| 段階 | 既定のしきい値 | 意味 |
| --- | --- | --- |
| （表示のみ） | 〜4時間 | 「未返信 1時間」のように経過時間だけ表示 |
| **要対応** | 4時間〜 | 顧客を待たせ始めています |
| **遅延** | 24時間〜 | 返信の目安を超えています |
| **重大な遅れ** | 48時間〜 | 長時間放置。最優先で対応してください |

こちらが返信すると段階は消えます。解決済み・クローズのチケットは対象外です。

しきい値は `.env` で運用に合わせて変更できます。

```bash
URGENCY_WATCH_HOURS=4
URGENCY_LATE_HOURS=24
URGENCY_CRITICAL_HOURS=48
```

> **経過時間は実時間で計算します（土日・時間外も数に入ります）。**
> 土日も交代で対応する運用のため、営業時間で割り引くことはしません。
> 金曜の夕方に届いて未返信のままなら、土曜の時点で「遅延」、
> 月曜の朝には「重大な遅れ」として表示されます。
> この挙動は単体テストで固定してあります（`tests/unit.mts`）。

## 署名

左下の **「担当者・判別ルール」** →担当者の **「署名を編集」** から登録します。
このアプリから返信すると、本文の末尾にそのまま付きます。

- 区切り線（`＊＊＊` や `---`）は**署名に含めてください**。アプリ側では足しません
  （独自の区切りがある署名に `--` を重ねると二重になるため）
- URL は送信時に自動でリンクになります
- 保存前に「送信されるプレビューを見る」で最終的な見え方を確認できます
- 返信欄の「署名を付ける」チェックで、1 通ずつ付ける／付けないを切り替えられます
- 未登録の担当者は、これまでどおり `--` と氏名だけが付きます

### 署名に氏名を入れておくと判別が楽になります

署名に担当者の氏名が含まれていると、保存時に**署名ルールとして自動登録**されます。
以後は Gmail から直接返信した分も、その署名から送信者を判別できます。
Gmail の「アカウントの委任」が使えない環境では、これが一番現実的な方法です。

## 「誰が返信したか」を判別する仕組み

上から順に試し、最初に一致したものを採用します。

| 優先 | 判別方法 | 仕組み | 確実性 |
| --- | --- | --- | --- |
| 1 | **このアプリから送信** | 送信時にログイン中の担当者を記録 | 確実 |
| 2 | **委任送信から判別** | Gmail の「アカウントの委任」で送ると `Sender` ヘッダーに本人のアドレスが入る | 高い |
| 3 | **送信者名から判別** | `サポート 山田 <support@…>` のように差出人名を出し分けている場合 | 中 |
| 4 | **署名から判別** | 本文の署名に含まれる文字列（氏名など）で判定 | 中 |
| 5 | **送信者不明** | 手がかりなし。画面に明示され、手動で設定できる | — |

### いちばん確実にする方法：Gmail の「アカウントの委任」

共有アドレスにパスワードを共有してログインするのではなく、
Gmail の **アカウントの委任** を使うと、送信者が自動的に記録されます。

1. 共有アドレスの Gmail で **設定 → アカウント → 「アカウントへのアクセスを許可する」**
2. 同僚の個人アドレスを追加
3. 同僚は自分の Gmail から共有アドレスに切り替えて返信する

これで `Sender` ヘッダーに同僚のアドレスが入り、このアプリが自動で判別します。
初めて見つけた委任アドレスは担当者として自動登録されます。

> Google Workspace 契約でない場合、委任機能は使えません。
> その場合は **署名ルール** を使ってください（次項）。

### 委任が使えない場合：署名で判別する

「送信者不明」のバッジを押すと、そのメールの署名らしい行が候補として表示されます。
担当者を選び、署名に必ず入る文字列（例: `木村`）を一緒に選んで保存すると、
ルールとして登録され、**過去のメールにも遡って自動判別されます**。

手動で設定したメールは、あとからルールを追加しても上書きされません。

ルールの一覧・追加・削除は左下の **「担当者・判別ルール」** から行えます。

## 使い方のコツ

- **左下の「Gmail と同期」** を押すたびに新着だけを差分で取り込みます（2 回目以降は速い）
- **「未返信」** フィルタで、お客様の最後のメールに返信できていないチケットだけ表示できます
- **「複数人が対応」** で、自分以外も触った会話を洗い出せます
- **「送信者不明あり」** で、判別できていない返信が残っているチケットを一掃できます
- サイドバーの **「未返信の経過時間」** から、放置しているものだけを取り出せます。
  件数は「その時間以上」の累計です（重大な遅れは遅延にも含まれます）
- 一覧右上の並び順を **「待たせている順」** にすると、長く待たせている順に並びます
- **「顧客一覧」**（左下）から顧客を選ぶと、その相手との**全案件を時系列**で追えます。
  「自分が請求書の件で返信 → 休みの日に同僚が別件で返信」のような流れも 1 画面で分かります。
  チケット画面の右側「この顧客との全やり取りを時系列で見る」からも開けます
- 入力欄は 1 つで、**押したボタンで動作が決まります**
  - **社内メモに残す** … このアプリ内にだけ記録。顧客には届きません
  - **○○ に返信を送信** … 実際にメールを送信。ボタンに宛先の名前が入ります

  タブでモードを切り替える形にはしていません。「メモを書いているつもりで顧客に送ってしまう」
  事故を防ぐため、外に出る操作だけを目立たせ、宛先を常にボタン上に表示しています。
  同じ理由で、送信のキーボードショートカットは用意していません
  （どちらの動作か曖昧になり、誤送信の原因になるため）。

## デモデータの操作

```bash
npm run seed:demo              # サンプル会話を作り直す（触った内容がリセットされます）
npm run seed:demo -- --reset   # サンプル会話だけ削除する
```

Gmail から取り込んだ本物のメールには影響しません（削除対象はデモ用のスレッドのみ）。

デモモードの安全策として、`DEMO_MODE=1` でも次の動作は行いません。

- Gmail との同期（API を直接叩いても拒否されます）
- メールの実送信（返信は記録だけ残り、顧客には届きません）

## テスト

```bash
npm run test:unit   # 文字コード・引用の切り離し・送信者判別ロジック（DB不要）
npm run test:api    # API の結合テスト（npm run dev と npm run seed:demo が先に必要）
```

`test:unit` は日本語メールで実際に問題になりやすい箇所を検証します。

- `ISO-2022-JP` / `Shift_JIS` / `EUC-JP` で書かれた件名・差出人名・本文のデコード
- `"山田, 太郎" <taro@…>` のようにカンマを含む名前の誤分割
- 返信の引用部分（`2026年7月20日(月) …:` や `On … wrote:`）の切り離し
- メール本文の HTML サニタイズ（`script`・`javascript:`・`onerror` の除去）
- 送信者判別の優先順位

Gmail への実送信だけは本物のアカウントが必要なため、自動テストの対象外です。

## よくあるトラブル

**「アクセスをブロックしました: このアプリは Google の審査を完了していません」**
OAuth 同意画面の「テストユーザー」に自分の Gmail アドレスを追加してください。

**「リフレッシュトークンを取得できませんでした」**
[Google アカウントのセキュリティ設定](https://myaccount.google.com/connections) から
このアプリのアクセスを削除して、もう一度ログインしてください。

**しばらく使っていたら急にログアウトされる**
OAuth 同意画面が「テスト」の場合、リフレッシュトークンは 7 日で失効します。
再度ログインすれば元に戻ります（データは消えません）。

**同期が途中で止まる / エラーが出る**
左下にエラー内容が表示されます。通数が多い場合は `.env` の `SYNC_DAYS_BACK` を
短くして試してください。API の制限に当たった場合は自動で待機・再試行します。

**送信者不明が多い**
Gmail の「アカウントの委任」を設定するのが最も確実です（上記参照）。
使えない場合は、各メンバーの署名から 1 件ずつルールを登録してください。
一度登録すれば過去のメールにも一括で反映されます。
